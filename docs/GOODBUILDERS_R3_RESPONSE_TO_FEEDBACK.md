**The "Claim Token" Anti-Pattern We're Avoiding:**

❌ User claims G$ → Immediately dumps for any other token → Never uses G$ again
✅ User claims G$ → Accumulates → Converts to mobile money for real expense → Repeats monthly

**Qualitative Indicators:**

By Month 3, I also want to hear users say things like:
- "I wait for my G$ UBI to pay my kid's school fees each month"

These statements indicate G$ has become **integrated into their financial life** rather than being a speculative asset.

### 5. Biggest External Dependency & Mitigation Plan

**Single Biggest Dependency: Kotani Pay API Reliability**

**Why This Is Critical:**

Kotani Pay is our mobile money off-ramp partner. They provide:
- M-Pesa, MTN Mobile Money, Airtel Money integrations
- Compliance/licensing in Kenya, Nigeria, Uganda, Tanzania
- Actual cash-out at recipient's mobile money account

**If Kotani Pay goes down or rate-limits us, our entire value proposition breaks.**

**Specific Risks:**

1. **API Downtime:** Kotani Pay service outage → conversions fail → user trust destroyed
2. **Rate Limiting:** We hit volume limits → conversions queue → frustrated users
3. **Regulatory Issues:** Kotani Pay loses license in a country → can't serve users there
4. **Fee Changes:** Kotani Pay increases fees mid-pilot → ruins our economics
5. **Slow Processing:** Conversions take 4-6 hours instead of 30 minutes → poor UX

**Mitigation Strategy (Within 3 Months):**

**1. Multi-Provider Backup (Week 1-4):**

Integrate **secondary provider** alongside Kotani Pay:
- **Option A: Mowblox** (Celo-native, supports Nigeria/Kenya)
- **Option B: Kash** (Stripe-like API, multi-country)

Implementation:
- Week 1-2: Research Mowblox/Kash APIs, get sandbox access
- Week 3-4: Build fallback integration (failover if Kotani Pay down)
- Logic: Try Kotani Pay → If fails → Try Mowblox → If fails → Manual queue

**Cost: 2-3 weeks dev time + $500 for testing**
**Benefit: 95%+ uptime even if one provider fails**

**2. Manual Fallback Workflow (Week 1):**

Build "operator mode" for manual processing:
- User requests conversion → Goes to queue
- I manually purchase mobile money using Kotani Pay dashboard or direct M-Pesa
- Mark conversion complete in system
- User gets SMS confirmation

**Cost: My time (sustainable for 100 users)**
**Benefit: Zero technical blocker can fully stop service**

**3. Clear SLA Monitoring (Week 2-3):**

Implement alerts for:
- Kotani Pay API response time > 10 seconds
- Conversion success rate < 90%
- Queue depth > 10 conversions
- Alert via Telegram → I can intervene quickly

**Cost: 1 day dev time**
**Benefit: Know about issues before users complain**

**4. User Expectation Management (Week 1):**

Be transparent about processing times:
- "Conversions typically arrive in 30-60 minutes"
- "During high volume, may take up to 4 hours"
- "You'll receive SMS confirmation when complete"

**Cost: Good UX copywriting**
**Benefit: Users aren't surprised by delays**

**5. Relationship Management with Kotani Pay:**

- **Week 1-2:** Set up direct Telegram/WhatsApp contact with Kotani Pay support team
- **Week 3-4:** Share our pilot plan, ask for priority support during pilot period
- **Ongoing:** Weekly check-ins to review volume, any issues, partnership evolution

**Cost: My time for relationship management**
**Benefit: Insider knowledge of issues before they impact us**

**6. Cash Reserve for Emergency Manual Processing:**

Keep $1,000 buffer in personal M-Pesa account:
- If Kotani Pay fails completely, I can manually send M-Pesa to users
- This covers ~15-20 emergency conversions
- Prevents catastrophic "no one getting money" scenario

**Cost: $1,000 cash buffer (returned after pilot)**
**Benefit: Ultimate safety net**

**Contingency Timeline:**

- **Week 1-4:** All mitigations implemented
- **Week 5-8:** Monitor closely, use backup provider if needed
- **Week 9-12:** Smooth operations or proven fallback patterns

**What Would Trigger Switching Primary Provider:**

If Kotani Pay shows:
- <85% success rate for 3 consecutive days
- >4 hour average conversion time
- 2+ full outages during pilot
- → Switch to Mowblox as primary, demote Kotani Pay to backup

### 7. Separating Real Usage from Incentive-Driven Behavior

This is a critical question because **subsidizing pilots often creates false demand**.

**My Approach to Measuring Real Usage:**

**1. Time-Boxed Subsidies (Clear Expiration)**

**Structure:**
- **First 5 conversions FREE** (gas + Kotani Pay fees subsidized)
- **Conversions 6-10: 50% off** (partial subsidy)
- **Conversion 11+: Full price** (2.5% fee as normal)

**Why This Works:**
- Users get free trial to learn the system
- Subsidy gradually ends (not cliff)
- By conversion 11, we're seeing real willingness to pay

**Measurement:**
- Track % of users who continue past subsidized period
- Target: >50% of users complete at least 1 unsubsidized conversion
- This proves they see value beyond "free money"

**2. Behavior Pattern Analysis (Not Just Volume)**

**Real Usage Signals:**
- ✅ User converts every 2-4 weeks (regular cadence)
- ✅ User converts amounts that match UBI accumulation ($30-60 range)
- ✅ User converts without prompt (initiates themselves)
- ✅ User contacts support with real questions ("I need to change my M-Pesa number")

**Incentive-Driven Signals:**
- ❌ User converts exact minimum to qualify for subsidy, then stops
- ❌ User converts random amounts with no pattern
- ❌ User only converts when reminded (not self-initiated)
- ❌ User ghosts after subsidy period ends

**Measurement:**
- Cohort analysis: Month 1 users still active in Month 3?
- Conversion frequency distribution: Is there a natural rhythm emerging?
- Support ticket content: Real problems or just "where's my free money?"

**3. Qualitative User Interviews (Ground Truth)**

**Schedule:**
- **Week 4:** Interview 10 early users
- **Week 8:** Interview 20 users (mix of active and churned)
- **Week 12:** Interview 30 users for post-pilot feedback

**Key Questions:**
- "What do you use the mobile money for?" (Specific = real, Vague = gaming system)
- "Would you still convert if it cost $2?" (Willingness to pay)
- "How often do you plan to convert?" (Does user have a mental model?)
- "How did you explain this to family/friends?" (Can they articulate value?)

**Real Usage Example:**
> "I convert every 2 weeks when I have $40 in G$. I use it for my kid's school lunch money. I'd still do this if it cost $1-2 because Western Union charges me $6 to send $40."

**Incentive-Driven Example:**
> "I converted a few times to try it out. It was cool that it was free. I'm not sure when I'll do it again. Maybe if there's another reward."

**4. Cohort-Based Retention Analysis**

**Structure:**
- Month 1 Cohort: 30 users
- Month 2 Cohort: 35 users
- Month 3 Cohort: 35 users

**Track Each Cohort:**
- % converting in weeks 2-4 after first conversion
- % converting in weeks 5-8 after first conversion
- % converting in weeks 9-12 after first conversion

**Healthy Pattern (Real Usage):**
- Month 1 cohort: 70% active in Week 4, 60% active in Week 8, 50% active in Week 12
- Slow decay = people finding natural usage patterns

**Unhealthy Pattern (Incentive-Driven):**
- Month 1 cohort: 90% active in Week 4, 30% active in Week 8, 10% active in Week 12
- Sharp drop = people only here for free stuff

**5. Conversion Amount Distribution**

**Real Usage Pattern:**
- Most conversions clustered around $30-60 (matches 2-4 weeks of UBI)
- Some larger conversions $80-100 (users saving for specific expense)
- Very few tiny conversions <$10 (not worth the hassle for real users)

**Incentive-Driven Pattern:**
- Lots of tiny conversions $5-10 (gaming rewards)
- No clear clustering (random amounts)
- Fewer large conversions (not accumulating for purpose)

**Measurement:**
- Plot histogram of conversion amounts
- Look for natural peaks (indicates purposeful accumulation)
- Outliers suggest either power users or gaming

**6. Referral Quality (Not Just Quantity)**

**Real Usage Referrals:**
- "My mom started claiming G$ because she saw my M-Pesa arrivals"
- Referrals convert within 1-2 weeks (excited about value)
- Referred users have high retention (vetted by referrer)

**Incentive-Driven Referrals:**
- "I invited 10 people to get rewards"
- Referrals never convert (just signing up for incentive)
- Low quality (random internet strangers, not real social network)

**Measurement:**
- Track referral conversion rate (% of referred users who complete conversion)
- Target: >40% of referrals complete conversion (vs <10% for gamers)
- Interview referrers: "Why did you invite [person]?" → Real reason or reward chasing?

**7. NPS Survey with Open-Ended Feedback**

**Timing:**
- After 3rd conversion (user has enough experience)
- Month 3 end (final survey)

**Question:**
> "How likely are you to recommend Drip's G$ → mobile money conversion to a friend? Why?"

**Real Usage Responses (Promoters, 9-10):**
> "10/10 - This saved me so much in Western Union fees. I send money to my mom every month now."

**Incentive-Driven Responses (Detractors, 0-6):**
> "7 - It was cool to try but I don't really need to convert G$ that often."

**Measurement:**
- Target NPS: >60 (indicates real value)
- NPS <30 = mostly incentive-driven, pivot needed
- Read open-ended responses to understand "why"

**8. Post-Subsidy Cohort (Control Group)**

**Experimental Design:**

- **Cohort A (30 users):** Full subsidies (first 5 conversions free)
- **Cohort B (20 users):** No subsidies (pay 2.5% from start)

**Hypothesis:**
- If demand is real, Cohort B should still convert (maybe less frequently, but measurable)
- If demand is fake, Cohort B won't convert at all

**Measurement:**
- Compare Cohort A vs B conversion rates
- If Cohort B >50% conversion rate = Real demand
- If Cohort B <20% conversion rate = Purely incentive-driven

**Ethical Note:** Cohort B users aren't "losing out" - they're paying market rate. We'll support them extra to ensure they succeed.

**Summary of Approach:**

I'm **not trying to maximize user count or volume** during subsidized period. I'm trying to find the **20-30 users who genuinely need this** and would pay for it.

Success = Even 30 users converting regularly at full price by Month 3.

Failure = 100 users during free period, <10 users after subsidy ends.

I'd rather have **30 real users** than **100 incentive tourists**.
